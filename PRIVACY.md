# Privacy and data handling

This document describes SuperX 1.0.0, including image inputs for published-post and manual draft checks through Grok subscription OAuth, API Key or official local Grok. Last updated: 2026-10-24. Draft text and supported attached images are sent only when you explicitly request a draft check. Release availability and platform-specific acceptance are documented separately in the [connection guide](docs/CONNECTIONS.md#acceptance-scope).

## Unreleased security hardening

Known Money, payment, wallet, account, settings, authentication, private-message and standalone Grok routes are excluded from feed and draft processing. Direct navigation is excluded in the manifest; runtime checks also cover single-page navigation and encoded paths. Entering an excluded route cancels that page's tasks, removes its SuperX UI and clears its retained feed/draft state. This does not delete previously saved history, recall submitted content or guarantee that provider-side work stops. After opening an excluded page directly, reload a supported X page to activate SuperX again.

The extension still has access to the X origins. Route guards are application controls, not a security boundary against a malicious extension update or an unknown future route. Use a separate research profile and an X account without payment funds for SuperX; keep wallets and X Money in a clean financial environment. Manual feed controls reject synthetic page events. API Key and OAuth inference both omit cookies, reject redirects and avoid HTTP caching/referrers.

## Setup and control

New installations default to **Sign in · The X Subscription**: browser-only OAuth opens the official xAI device-authorization page for you to approve the code and access. **Grok API Key** uses your own Key; **Grok Build · Local CLI / ACP** uses the official locally installed client, generated command and optional local-address access. Existing selections and independent settings remain intact. Nonempty older settings without a source, or missing/empty settings with legacy credentials, keep API. No route automatically substitutes another credential or changes an account budget. There is no separate SuperX data-consent checkbox or ZDR-attestation step; OAuth authorization is your own confirmation on the official site. Pause analysis to stop automatic requests. Clearing or replacing an API Key cancels queued and active work and clears its previous session credential and cache; this does not recall data already sent.

## What is sent to xAI

In API Key and OAuth modes, when analysis is enabled, the selected connection is available and a visible post enters the queue, SuperX sends an HTTPS request directly to `api.x.ai` from its extension background worker. All three routes use this post context:

- The canonical original post URL and post ID.
- The author's currently displayed post text, its language mark, author label and timestamp.
- Media presence, eligible X-hosted images and their accessible descriptions, plus available quoted-post context. Published target posts, reply parents, thread roots/ancestors and up to two nested quotation levels can supply image inputs. Each source contributes up to four images; a request includes at most 24 unique images and may omit further images under its context budget. A published video thumbnail is one still frame, not the video. Supplying an image is not a guarantee that the model understood it.
- Your selected model, reasoning effort, answer language, search settings and effective fact-check instructions, including custom prompts if selected.
- The existing Fact Check for an optional comment-drafting request. Fact Check itself uses one generation request and does not receive an earlier explanation.

The selected API Key or OAuth access token is sent to xAI as the request's Bearer authentication credential, never to the X page. Search-enabled requests ask xAI's tools to retrieve the original post and relevant evidence; provider tools may retrieve further posts, pages or media. API/OAuth requests supply eligible published-image URLs as native image inputs. The provider retrieves those images; SuperX does not independently preload every complete post or video. In local Build mode, the extension fetches eligible image bytes from the restricted `pbs.twimg.com` media paths with credentials omitted, redirects refused and no HTTP cache, checks PNG/JPEG content, then sends base64 image blocks over the local connection. It checks the official runtime image capability before sending; unsupported, dropped or unreadable images produce an error rather than a silent text-only retry. Build has an additional 8 MiB combined image-byte limit per request.

OAuth device-code creation, token polling/refresh and best-effort refresh-token revocation use fixed HTTPS endpoints under `auth.x.ai/oauth2/`. The browser opens only a validated official `accounts.x.ai` or `auth.x.ai` device-authorization page. That site's own authentication, cookies and policies apply to your visit; SuperX does not read its cookies or your account password. The short user code and authorization link appear only in trusted extension UI, not in the X feed script. Device codes, access tokens and refresh tokens are excluded from public configuration, generated history and diagnostics.

This route uses the shared public Grok OAuth client, so the official page can display **Grok Build**, rather than a separately registered SuperX application. New authorizations request only `openid offline_access grok-cli:access api:access`. They do not request the optional `profile` or `email` claim scopes ([OpenID Connect §5.4](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims)), and SuperX does not fetch or use account-profile information. `offline_access` requests refresh access ([§11](https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess)); Grok's access scopes and the actual grant remain provider-controlled ([OAuth 2.0 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)). Login checks the model directory at `api.x.ai/v1/models` without a test generation or CLI identity headers. No universal plan entitlement or official partnership is claimed.

Existing connected credentials are not automatically signed out, and reducing a new request's scope does not retroactively shrink an old grant. A pending device login with a different stored scope is discarded and must be started again. Sign out and authorize again to obtain a new grant; plan eligibility, models, allowance and charges remain provider- and account-dependent.

In Grok CLI / ACP mode the extension sends the post context, effective instructions, selected model/effort and optional earlier Fact Check directly over a loopback WebSocket to the official Grok service started by the user. The address is fixed to `127.0.0.1`, with a selected local port. That client authenticates and sends requests to its provider. In this local mode, SuperX does not receive, read or copy the official client's OAuth tokens, login files or X cookies. The generated command points official Grok at its own default login file using its supported auth-path setting while giving it an isolated temporary Grok home / working directory; personal configuration is left unchanged. This mode does not use the extension's API Key. Provider Build/account terms and retention rules apply; the API `store: false` option below does not establish Build retention behavior.

SuperX supplies a restricted per-session profile, checks the actual local-function count, and rejects filesystem, terminal and permission requests. The generated command disables imported coding/MCP integrations. These restrictions are not an operating-system sandbox or protection against a compromised runtime. Install Grok only through official instructions and keep its local service bound to loopback.

The local service uses a randomly generated connection code, distinct from an API Key or account password. SuperX sends it only to the fixed loopback address as the official WebSocket handshake credential. It is not sent to X or a SuperX server and is excluded from public settings, post history and diagnostic text. SuperX encrypts its saved copy locally, with the same protection limits as remembered API Keys. The generated command and clipboard can contain the code, and shell history or local debugging tools may retain it. Anyone with the code and local access may be able to control that official service; stop the old service and generate a new code if exposed. The official service does not itself require a SuperX-specific browser origin. Neither telemetry nor a SuperX relay is added.

The extension does not restrict analysis to public posts. **Protected posts, replies and posts visible in likes or bookmarks can be included if they appear as supported post elements on an enabled page.** A provider may be unable to retrieve them by URL, but the visible text can still be sent as supporting context. Pause SuperX before opening pages whose contents you do not want sent.

Direct-message and standalone Grok pages are excluded from analysis and history recording. The extension does not read X authentication cookies, access the browser's history of other sites or send X session credentials to xAI. Its separate, on-device history records supported X posts actually visible while SuperX and history recording are enabled, as described below. It does not post, reply, like or repost. Comment suggestions remain drafts; a click copies a selected draft through the browser clipboard API.

## Manual draft checks

On supported X post/reply composers, **Check** sends the text snapshot and supported attached images present when you explicitly click that control. Only at that click does SuperX fetch the selected native upload previews (same-origin blob URLs or eligible X media previews); it does not inspect arbitrary local files or the clipboard. Up to four PNG/JPEG images with a combined image-file size of 8 MiB before base64 encoding are accepted, including an image-only draft. A failed, unsupported or oversized image stops that attempt with an error; SuperX does not silently send only the text. Draft video attachments are not uploaded as image inputs and remain unchecked. Typing, changing the text, opening the editor or expanding an existing result does not by itself send another draft-check request. Pausing automatic feed analysis or collapsing its rail does not prevent an explicitly requested draft check. The selected account's allowance, billing, searches and provider rules still apply.

The request can include a new post's quoted posts, or a reply's available original thread post, earlier replies and direct parent. Canonical URLs and bounded text snapshots support interpretation of the draft; the draft remains the target. This context may include protected or non-public post text visible to you. Earlier thread snapshots can remain in page memory when X temporarily removes their DOM elements. A request retains up to six earlier thread posts (the root and nearest replies), plus the direct parent. Available quoted posts can include up to two nested quotation levels, with at most two quotations per level. Native previews without a reliable permalink may be included as text, author and time snapshots; SuperX does not invent a post URL or treat those snapshots as independently verified sources. Context is bounded and may be shortened to fit the request budget. The draft text and its supported attached images remain the target; contextual images only help interpret it. An unchecked-media flag can indicate excluded video or other attachments. It uses the selected model, reasoning, search tools and effective instructions, with the response language based on the draft's predominant text language, or legible image text when no draft text is present. Requests go directly to xAI in OAuth/API Key mode or through the user's official local Grok service in Build mode, with the same credential and provider-retention limitations described in this policy. No SuperX relay is involved.

Draft snapshots, captured image bytes/base64, reply context and generated findings remain only in page/worker runtime memory for that page's task. They are excluded from the answer cache, browsing-history records and local diagnostic log. Collapsing the panel, switching browser tabs or temporary editor replacement can preserve the same in-memory task; page navigation, reload or tab closure clears the page's retained drafts and results. This local cleanup does not recall a request already sent or delete provider-side records. An original post separately viewed in the feed can still be recorded by the ordinary browsing-history feature; this does not record the unpublished draft.

SuperX displays findings below the composer without editing or submitting its contents. Continuing to edit marks the existing result as out of date and requires another explicit check to update it. Draft checks do not automatically post, generate images or attach clipboard files.

## Third parties and network requests

The project does not operate an API relay, analytics service or telemetry endpoint. That does not mean no data leaves your device: analysis and comment requests go to xAI, whose handling is governed by its own terms, policies and account configuration.

SuperX's use and transfer of user data adheres to the Chrome Web Store User Data Policy, including its Limited Use requirements. Post content and related browsing activity are used only for factual-claim analysis, reply-drafting and on-device recent-history features and necessary caches; they are not used for advertising, data sales, credit decisions or unrelated profiling.

API requests set `store: false` in the xAI Responses payload. This describes the extension's request option; **it is not a guarantee that xAI retains no request data, logs or tool inputs**. Review the provider's current policies for your account before using non-public or sensitive material.

xAI's account configuration and terms remain applicable. Its [API security documentation](https://docs.x.ai/developers/faq/security) describes default retention and optional team-wide ZDR; its [Data Processing Addendum](https://x.ai/legal/data-processing-addendum), effective September 22, 2026, separately requires ZDR-enabled processing for Personal Data. Public posts can contain Personal Data. SuperX does not check or configure these provider-side requirements, and a normal Key or `store: false` does not establish compliance. See also the [API Enterprise Terms](https://x.ai/legal/terms-of-service-enterprise).

Model-provided Markdown is parsed locally. SuperX does not execute model HTML or load model-provided images. Safe HTTP(S) source links open only when clicked. Opening a source, the API console or a help link is a separate interaction with that website and its policies. X itself continues its usual page requests independently of SuperX.

## What remains on your device

| Data | Storage and lifetime |
| --- | --- |
| API Key with Remember Key checked | AES-GCM ciphertext in local extension storage (`apiKeyEncrypted`), until cleared or replaced; default preference for first setup and automatically restored after browser restart |
| Local encryption key | A separate, randomly generated, non-extractable CryptoKey in extension IndexedDB; removed when Remember Key is disabled or saved credentials are cleared |
| API Key with Remember Key unchecked | Browser session extension storage and necessary runtime memory; not deliberately persisted across sessions |
| OAuth login with Remember login checked | Refresh-token ciphertext in the separate `superxOAuthCredential` local record, encrypted with its own random non-extractable AES-GCM CryptoKey in extension IndexedDB; automatically restored/refreshed after browser restart without a password |
| OAuth access token / session-only refresh token | Restricted session extension storage and worker memory. Access tokens are never persisted in local extension storage; with Remember login off, the refresh token is also session-only |
| OAuth authorization state | A pending device challenge is kept in restricted session storage until completed/cancelled/expired or invalidated; local metadata records identity, rotation revision and storage preference. Safe model IDs, expiry and status are retained; unknown rotation outcomes are blocked instead of replayed |
| Obsolete plaintext or password-encrypted Key records | Plaintext is removed after successful migration; old password-encrypted records are not decrypted and remain only until successful migration, replacement or clearing |
| Settings, custom prompts, remember preference and last reported X interface language | Local extension storage until changed or extension data is removed |
| Completed published-post analyses and comment suggestions | Browser session result cache, reusable for up to 24 hours within that session, bounded to 160 entries and approximately 4 MB; removed when the browser session ends; manual draft checks are excluded |
| Recent X browsing history | Unencrypted, restricted local extension storage (`superxHistory`), retained for 24 hours after each post's latest view across browser restart; bounded to 1,000 posts and approximately 6 MB |
| Per-tab counters, collapse state and session interface language | Session extension storage |
| Local API diagnostic log | Restricted session extension storage (`apiRequestDiagnostics`): up to 30 API failures for 24 hours within the browser session; bounded redacted provider error details, safe failure categories, trace IDs, local times/duration, transport status and requested/server-reported model metadata; cleared by its separate Settings control or browser-session end |
| Active page snapshots, partial answers and queued jobs | Runtime memory while their page / worker remains active |
| Manual draft checks | Unpublished text and image snapshots (including bytes/base64), available reply context and findings in page/worker runtime memory only; not saved to the answer cache, browsing history or diagnostic log; page navigation, reload or tab closure clears the page's retained drafts/results |
| Local Grok connection code and port | Code encrypted in local extension storage with a separate local CryptoKey; restored into trusted session storage. Port is a local setting; credentials are not browser-synced |
| Official Grok prompts, turns and isolated home | Official-runtime memory and its temporary home/working directory. Normal command exit attempts temporary cleanup; crashes or forced termination can leave remnants, and the provider's own retention rules apply |

The diagnostic log deliberately excludes request bodies, API Keys, OAuth credentials and post/prompt fields; current request context and known request credentials are removed from provider messages before they are retained. OAuth lifecycle errors use fixed categories without raw token-response prose. It is not a raw HTTP or browser log. Error text originates with the provider, so review operational details and trace IDs before sharing a copied log. Copying does not upload it, and clearing it does not remove history, saved Keys or answer caches. Legacy account-limit and capacity-pause session records are discarded on startup; a failed task no longer pauses other posts.

The official client's login remains in its own default storage. SuperX's Clear saved Key does not log that client out, revoke subscription access or remove its provider records. Use official Grok logout to end that login. Removing SuperX does not uninstall or stop the official client. Runtime/account services can make supporting requests such as session titles, so one SuperX Fact Check prompt is not a promise of exactly one upstream network request.

Disconnecting the WebSocket alone does not stop an official-service task. SuperX sends explicit cancellation and session-close requests; after a disconnect it can reconnect only for those control requests, never to replay a prompt. If stopping cannot be confirmed, SuperX reports it. Press Ctrl+C in the service terminal to stop it manually. Work already submitted may still consume provider usage.

Session cache entries contain generated text or comments, sources, model and usage metadata, completion times and cache identities. Those identities can include the post URL, selected settings, effective prompts, and—for comment drafts—the visible post / quotation snapshot and earlier analysis. Cached output can repeat the original post's text or image contents. Raw image bytes are not saved in the result cache. Treat the cache as potentially sensitive, not merely an anonymous performance index. Cache contents are not deliberately saved to persistent local storage. On upgrade, old local caches are removed rather than imported.

Cache reuse and generated history views are separated by connection source and OAuth authorization identity. Switching sources, signing out or authorizing another OAuth account does not expose the previous source/account's generated answers or comments in the new context. The locally recorded post visits are independent and remain until expiry or deletion. This isolation is not forensic erasure of previously stored history output or of answers already visible in a page.

Browsing history is a separate persistent record, enabled by default. While SuperX and history recording are enabled, supported posts actually visible on X are recorded without a dwell delay, even without an available API Key or completed analysis. It stores canonical post URLs/IDs, displayed text (up to 12,000 characters), author labels, language, media-presence flags, first/latest viewing times and visit counts. Available generated answers (up to 30,000 characters), up to 20 safe source links, model/Token metadata and up to three comment drafts can be retained with a post. Protected or non-public posts can be included. This is not a full post archive; it does not save image files or retrieve unseen post text just to populate history.

History stays on the device and is neither uploaded as a history collection nor synced. Viewing, searching or expanding saved answers makes no API requests and does not automatically fetch remote images. Original-post and source links open their websites only when clicked. History is not an API-response reuse cache: viewing it does not resume generation. Entries are merged by post ID and ordered by the latest view. Viewing a post again restarts its 24-hour period; reaching the count or byte limits may remove older entries sooner.

Remember Key encrypts your API Key with AES-GCM and a random local encryption key. The ciphertext and encryption key are stored separately: ciphertext in `chrome.storage.local`, and the non-extractable CryptoKey in the extension’s IndexedDB. On browser startup, the worker automatically decrypts the saved Key into restricted session storage. There is no SuperX password, lock or unlock step. With Remember Key disabled, a new browser session requires entering the API Key again.

Settings, credentials and history are not stored through browser sync. Settings, custom prompts and browsing history are not encrypted; avoid placing credentials or private material in prompts. API Key, OAuth refresh-token and local-connection encryption use independent keys and records; clearing one does not destroy the others. Automatic encryption protects a saved credential if only its ciphertext or local-settings storage is exposed. It does not protect against access to both ciphertext and extension IndexedDB, the full browser profile, backups containing those records, or a compromised runtime or device. Non-extractable means Web Crypto cannot export the CryptoKey; it does not bind the key to operating-system credentials or hardware. Storage is restricted to trusted extension contexts. OAuth tokens are used only by the worker; trusted UI receives safe status and the temporary user code/link, and the feed script receives only readiness/identity status, never those credentials or the saved history collection.

OAuth refreshes are serialized. SuperX records a durable rotation intent before consuming a refresh token and confirms the rotated storage pair before using the replacement. Network uncertainty, mismatched records or failed persistence require sign-in again instead of repeated use of a possibly consumed token. Token expiry is based on the provider's returned lifetime. Background alarms and on-demand checks refresh authorization without sending a generation prompt; a login or refresh can itself contact the provider even when no post is being analyzed.

An upgrade can reuse an existing valid plaintext local Key or an available session Key from an older version. When Remember Key is selected, it encrypts that Key before removing the plaintext record. With session-only storage selected, persistent Key records and the local encryption key are removed. If the saved ciphertext or encryption key is missing or damaged, enter the API Key once again. The current version does not decrypt older password-encrypted records; obsolete records remain only until successful migration, replacement or clearing. Obsolete data-consent fields are ignored and do not control analysis.

## Expiry, clearing and controls

- **Pause / disable:** stops automatic analysis and new history recording. It does not delete the Key, cache or existing history. Cancellation can occur after a request has reached xAI, and already sent work may still be billed.
- **Collapse:** cancels waiting work and restores X's sidebar. Already started work may finish; collapse is not equivalent to clearing credentials or pausing all requests.
- **Clear saved Key:** cancels tasks and removes saved ciphertext, the separate IndexedDB encryption key, obsolete Key records, the session credential and session cache. Your remember preference remains selected or unselected as before. It does not delete browsing history, revoke the Key at xAI or erase an already sent request.
- **Replace Key:** cancels old tasks and clears the previous session cache before applying the replacement Key. Existing browsing history remains. Already sent work may still be billed.
- **Clear cache:** removes the session result cache and any legacy local cache. It does not erase your Key, settings, browsing history, provider records or answers already displayed in an open page; refresh that page to clear its displayed results. New completed requests can subsequently create new cache entries.
- **History controls:** turn off Save browsing history to stop new records and answer updates while retaining existing records until expiry. Delete removes one saved post and its answer/comment copies; Clear history removes all saved history. These controls do not delete the Key, session cache or provider records, or an answer displayed in X. A later actual view may create a new record while recording remains enabled.
- **Uncheck Remember Key and save:** removes saved ciphertext, the IndexedDB encryption key and obsolete persistent Key records, and keeps the current API Key only in session storage. Existing session-only credentials are not automatically migrated to persistent storage without choosing Remember Key.
- **OAuth Cancel / Sign out:** cancellation invalidates the pending device login; sign-out clears this connection's session/local records and encryption key, cancels its tasks and attempts to revoke the latest known refresh token. Late results cannot restore a cancelled login or overwrite a newer one. These controls do not erase recorded post visits, saved API/local credentials, browser website sessions or provider records; revocation cannot be guaranteed when the provider is unreachable.
- **Uncheck Remember login:** removes the persistent OAuth refresh-token copy and keeps the active login only in restricted session storage; a new browser session needs sign-in again. Source changes preserve existing connected credentials but never use them as automatic fallback.

Clearing extension records is not a guarantee of forensic erasure from the device, older backups or browser storage remnants.

The cache's 24-hour period is a **reuse expiry**, not a wall-clock deletion timer within an open browser session. Expired, malformed, future-dated or over-budget cache entries are pruned when the background worker initializes and when new entries are saved. Cache data can remain in session memory until that cleanup, explicit clearing or the end of the browser session. Closing X alone does not clear the session cache.

History's separate 24-hour lifetime runs from the post's latest view. Expired entries are excluded from history views and removed on startup, history reads/writes and an hourly `alarms` cleanup. Browser shutdown, scheduling delays and storage errors may postpone physical deletion; a timer does not guarantee exact-time erasure. History persists across browser restart until expiry or removal and can be pruned earlier to meet storage limits. Uninstalling or removing extension data through the browser is a broader removal step; provider records are separate.

If a storage write fails, session cleanup can be delayed. Expired entries still remain excluded from reuse in worker memory, and a later cache write retries without preventing the extension from starting. Removal of a legacy local cache can also fail and should be retried by reopening the extension or clearing its data.

There is no extension-level monetary budget or post-count cap. All visible eligible posts can trigger provider usage or paid work. Keep automatic analysis paused until you have configured a connection and reviewed the matching account's limits and billing.

API Key and CLI / ACP transient failures in fact checks and comments retry after 3 seconds, up to 5 additional attempts per task, using the same selected provider, model and reasoning settings. Retries resend that task's context and can consume additional provider allowance or paid usage. Invalid credentials, account/balance restrictions, unsupported settings, output limits and unconfirmed local cancellation are not automatically retried. OAuth generation is never automatically replayed after an accepted HTTP 200 response, in-stream error, incomplete output or timeout. An initial HTTP 401 rejection can refresh authorization once and make one recovery request; another rejection requires sign-in. A failed task does not stop other posts. Started answers remain in memory when scrolling or X's timeline virtualization removes a post from view; returning to it restores the task instead of automatically starting it again. The page retains up to 100 inactive detached cards in addition to active requests, and discards them on navigation or page closure.

## Permissions

| Permission | Why it is used |
| --- | --- |
| `storage` | Local settings, independently encrypted API/OAuth/local credentials, recent browsing history, restricted session credentials and result cache |
| `alarms` | Expired-history cleanup and OAuth device polling / token refresh; these authentication calls do not send a generation prompt |
| Optional `http://127.0.0.1/*` | User-granted access for the official local Grok WebSocket connection; not requested for API mode. Actual connections use `ws://127.0.0.1` and the configured port only |
| `https://x.com/*`, `https://twitter.com/*` | Observe supported post elements, follow theme / language and show the result column; read a supported composer text/image snapshot when its Check control is explicitly clicked |
| `https://api.x.ai/*` | Call the provider from the background worker |
| `https://auth.x.ai/*` | Fixed OAuth device authorization, token exchange / refresh and revocation endpoints; newly added host access can require upgrade approval |

The extension does not request the browser's `cookies` or `history` permission or broad access to all websites. Its own recent history comes from visible supported X post elements, not the browser's global browsing-history database. Matching a site for content-script injection is broader than the actual supported analysis paths; the runtime excludes direct messages and standalone Grok / settings flows.

## Reports and development

Automated tests and local UI previews use simulated browser APIs and credentials. They do not read the installed extension's real Key or perform paid analysis. Any separate real-account acceptance requires the user's own fresh official authorization. Screenshots, console captures and issue reports can still expose private content: redact Keys, OAuth credentials/codes, account details, protected posts and request payloads before sharing. Follow [SECURITY.md](SECURITY.md) for vulnerabilities.

Changes to collected fields, host access, storage or provider calls require this document to be updated alongside the code.

Public support uses [SuperX Issues](https://github.com/bwjoke/SuperX/issues); sensitive security reports follow [SECURITY.md](SECURITY.md). The website's privacy address is [superx.vip/privacy/](https://superx.vip/privacy/). The website is deployed separately from the extension and this repository. Its publication and accessibility must be checked separately from local documentation changes.
